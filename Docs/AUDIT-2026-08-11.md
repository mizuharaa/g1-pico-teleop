## 1. Why MuJoCo shows no movement — CONFIRMED live, not a code mystery

The sim robot stands in velocity mode and ignores the headset because **no body
data has ever reached the retarget node**. Verified live at 11:57:

- PC service IS listening on `192.168.123.2:63901` — but has **zero clients**:
  the headset app is not connected to it (`/tmp/rehearsal_node.log` repeats
  `[PicoReader] head_pose_dead — app not connected to 192.168.123.2`).
- The node blocks in `init_xrt()` (`holomotion_teleop_node.py:946-966`) BEFORE

- `--fast` boots to velocity mode; tracking needs key `3` (B) AND
  `_is_vr_ready_for_motion()` ≈13 buffered frames — with no stream, B is
  silently refused (`policy_runtime.py:227-232`) and nothing is printed
  (`Rig(verbose=False)` mutes all PolicyRuntime logs, `sim_port.py:44-52`).

### Compounding faults that made "10+ prompts" fail
1. **Supervisor thrash**: `run_rehearsal_supervised.sh:52-67` stall-kills the
   node with `kill -9` every 12 s while it is still waiting for body data —
   there is no startup grace period. Each kill bypasses `xrt.close()` and can
   escalate to recycling the PC service, which resets the app's Mode. The
   operator physically cannot finish headset setup inside a 12 s window.
2. **Earlier today**: `run_rehearsal_supervised.sh` was edited in place at
   11:44 while running (started 11:41) — bash re-read a stale byte offset and
   the supervisor died silently, orphaning node pid 1264331, which then held
   the one allowed SDK client and poisoned every retry (one-SDK-client limit).
   Rule: after editing the supervisor script, `pkill -f run_rehearsal_supervised;
   pkill -f holomotion_teleop_node` before relaunching.
3. **No orphan cleanup anywhere**: `run_rehearsal_supervised.sh:29` pkills only
   the mjviewer; `sim_with_pico.sh:45` only checks for the supervisor. Stale
   nodes both hold the SDK client and own the `bind(tcp://*:6001)`.
4. **Contradictory IP instructions**: HANDOFF/session_up say enter `10.42.0.1`
   (robot); `sim_with_pico.sh` says `192.168.123.2` (laptop). Both services

## 2. Why nothing survives headset-off / sleep / reconnect / reboot

### Root bug B1 (real code bug, biggest single fix)
`XRoboToolkit-PC-Service-Pybind` `bindings/py_bindings.cpp:31,217`:
**`BodyDataAvailable` is a write-once latch** — set true on the first body
frame, NEVER cleared. `PXREAServerDisconnect` / `PXREADeviceMissing` (:97-105)
only print. Consequences:
- After any mid-session headset-off, all `head_pose_dead` diagnostics are
  unreachable (they live under `if not is_body_data_available()` —
  `holomotion_teleop_node.py:142-169`) → the node goes silent-frozen.
- The supervisor's "wedged service" detector greps for those now-unprintable
  lines → dead code in exactly the scenario it was written for.
- Readers busy-spin at ~1 µs sleep on the frozen timestamp
  (`holomotion_teleop_node.py:171-175`, `local_retarget.py:137-139`) — a hot
  core stolen from a 50 Hz loop on the Orin during degraded state.
Fix: clear the latch (under bodyMutex) on disconnect/device-missing; Python
belt-and-braces: treat "timestamp unchanged > 1 s" as not-available; expose
`reader.is_live()`; log explicit `stream_dead`/`stream_live` transitions.

### Other resilience gaps (ranked)
- **G1 supervisor thrash / no grace period** (see §1). Fix: 90 s startup grace
  + SIGTERM-then-SIGKILL (stop() runs `xrt.close()` → no leaked SDK clients).
- **G2 no adb headset hardening**: adb exists in tools/platform-tools, wireless
  adb known-working. Add `scripts/headset_hold.sh`: `svc power stayon true`,
  `settings put system screen_off_timeout 1800000`, `settings put secure
  sleep_timeout -1`, poll `dumpsys power`/`mResumedActivity` and `am start`
  the app on wake. (Pico proximity-disable key needs on-device verification.)
- **G6 headset Wi-Fi not pinned**: `adb shell cmd wifi forget-network <id>` for
  VNG/iPhone SSIDs + `cmd wifi connect-network g1-teleop wpa2 teleop12345`
  makes "headset flees the AP" impossible rather than unlikely.
- **G3 Mode=None on reconnect never investigated at app level**: try
  shared_prefs push/pull (`run-as`), else recorded `adb shell input tap`
  sequence replayed on reconnect — kills the most-repeated manual step.
- **G4 container has no restart policy** (`start_teleop_container.sh:18-21`).
  `--restart unless-stopped` — but ONLY after confirming the FSM boots into
  ZERO_TORQUE and cannot command motion unattended (safety change).
- **G5 PC service unsupervised in-container**; `sdk.init()` called once ever
  (`local_retarget.py:180-183`) — a service restart permanently orphans the
  reader. Add respawn loop + reader-side re-init when timestamp stalls.
- **G8 nothing detects a dead safety watchdog** (`joint_watchdog.py` armed once
  by session_up; if it dies mid-session, silence). Highest-danger gap.
- **G7 `Hotspot-1` name assumed** in session_up.sh:101; autoconnect "fix" never
  verified (silent no-op possible).
- Structural: on the robot, PC service is a child of `launch_runtime.sh` —
  any policy restart kills it → drops headset TCP → Mode resets. Policy
  restart and headset re-setup are inseparable by construction.
- Robot has NO supervisor at all — everything self-healing exists only in the
  laptop rehearsal path.

### Session-survival matrix (current behavior)
| Interruption | Auto-recovers | Still manual |
|---|---|---|
| Headset off-head | policy falls back to velocity; robot keeps balancing | B press to re-enter tracking; Mode re-tick; re-calibrate |
| Headset sleep→wake | StreamResumeGate swallows zombie frame (good code!) | Wi-Fi re-assoc not guaranteed; Mode; B |
| App reconnect | (laptop only, mostly broken by B1) | full re-setup: IP, Send, Mode, calibrate, B |
| Robot reboot | AP only (after session_up ran once) | container (no restart policy), session_up, full headset setup |
| Laptop reboot | nothing | session_up, estop console, watchdog — and nothing warns the safety rail is down |

## 3. Why motion is choppy — three confirmed mechanisms + one NEW startup blocker

### 🔴 A0 — NEW BLOCKER: the deployed yaml self-contradicts and will refuse to start
`orin_docker.yaml:41` `reference_source: "pico_local"` + `:73`
`motion_observation_backend: "cpu"` → unpatched `policy_node_29dof.py:517-523`
**raises RuntimeError("reference_source=pico_local requires Warp CUDA
Observation")** at setup. This exact yaml is what deploy_cpp_patch.sh shipped
on 08-11, and session_up.sh's gate check ENFORCES the broken half. The next
`holomotion teleop` on the robot fails before any motion. Options:
(i) `reference_source: "zmq"` + cpu backend (retarget out-of-process), or
(ii) keep warp backend + add an offline Warp warmup pass at node setup
(the raw `auto`→warp path is what caused the 08-10 fall: 2.65 s JIT + 46-52
ms/step). Fix the session_up gate to check the PAIR, not one half.

### A1 — Zero smoothing end-to-end (confirmed, primary chop source)
`policy_runtime.py:502-562`: onnx action × scale + default → published verbatim
→ `main_node.cpp:614-636` writes it as a hard PD setpoint at 500 Hz ("Use
policy kp/kd values directly without torque limiting"), zero-order-held 10
firmware ticks. No filter, slew limit, or interpolation anywhere.
Sim measured ~0.5 rad/20 ms ankle steps **under a perfectly smooth analytic
reference** — the chop is substantially intrinsic policy output, so reference
cleanup alone cannot fix it. Ankle: 0.5 rad × kp 28.5 ≈ 14 N·m instant spike.
Obs constraint is narrow: `last_action` = 1 frame of RAW action
(`observation_evaluator.py:982`), so a post-store slew limiter (like the
existing soft-start/blend hunks) keeps the invariant. Prefer a per-joint slew
limiter (no-op in normal motion, clips outliers) over an EMA (always-on bias,
policy winds up against it).

### A2 — Reference-side aliasing: 91 FPS → 50 Hz with no interpolation/de-dup
`local_retarget.py:238-251` takes latest-frame-only; `last_sample` never used →
**no de-dup** (the zmq path DOES de-dup, `policy_node_29dof.py:1065-1067`).
Device timestamp discarded — `sample_time = policy tick arrival`
(`policy_node_29dof.py:1101-1107`); Warp obs builder assumes a FIXED uniform
20 ms grid (`gpu_motion_observation.py:77-83`). Result: reference dof_vel
swings ~±45% tick-to-tick even with a perfectly smooth operator (2-frame vs
1-frame advance beat), and TCP bursts inject zero-velocity + double-jump
pairs. `slerp` exists in utils but has zero callers. Also n_fut_frames=10 →
200 ms built-in reference lag → operator over-corrects → more chop.

### A3 — Transport & radio: gRPC-over-TCP on an accidental 2.4 GHz AP
The PICO stream is gRPC/HTTP-2/TCP (no UDP path exists in the SDK) → one lost
802.11 frame = head-of-line stall then burst = duplicates + jump (feeds A2 and
the max_data_age bounces). The robot AP is on 2.4 GHz **by omission** — no
band was ever set (`session_up.sh:104`); HANDOFF's "fallback to bg" was
already the accidental default. Fix: `nmcli con modify Hotspot-1
802-11-wireless.band a 802-11-wireless.channel 36` (re-test headset assoc).

### A4 — Corrections to the HANDOFF twitch analysis
- The "instant gain swap" in mode transitions is a numerical NO-OP: velocity
  and motion ONNX carry byte-identical stiffness/damping/action_scale. Only
  the target snapped; the blend patch fully covers suspect #1.
- Blend coverage gap: **A button** during POLICY (`policy_runtime.py:150-151`
  → `enable_velocity_policy`) snaps unblended. 15-min fix: reuse blend capture.
- Suspect #3 is UNMEASURABLE from existing logs: `timing_debug_enabled: false`
  in orin_docker.yaml:77 → `policy_total_ms` was never recorded; repo contains
  zero timing CSVs (outputs/ logs are empty files). Flip it on — it's free.
- pico_local runs the full IK retarget synchronously INSIDE the 50 Hz loop,
  sharing the Orin GPU with TRT inference — structural overrun risk.
- smoke suite feeds an analytic 50 Hz reference: it does NOT test A2 at all,
  and `b_press_and_track` computes max_target_step but never gates/reports it.

### Ranked fixes (chop)
1. Resolve A0 yaml contradiction + fix session_up gate (blocks everything).
2. `timing_debug_enabled: true` → first-ever real timing data (5 min).
3. Per-joint slew limit on target_dof_pos_real post-store (2-4 h + sim A/B);
   gate max_target_step in the smoke suite.
4. De-dup pico_local like zmq path (1-2 h).
5. Interpolate reference to policy tick (ring buffer + lerp/slerp, true
   sample_time, kill the fixed 20 ms grid) (0.5-1 d).
6. Extend smoke suite: 91 Hz source, duplicates, jittered ticks (3-5 h).
7. AP → 5 GHz (30 min). 8. Bake TRT cache + Warp warmup. 9. Blend A-press.

## 4. Comparison vs NVIDIA GR00T sim-teleop-and-WBC

Their pipeline: XR headset browser client → CloudXR → Isaac Lab-Arena sim →
HDF5 demos (galileo_g1 tasks). Key differences and takeaways:
- **They don't stream full-body pose.** Teleop input is OpenXR controllers +
  joysticks; the WBC abstracts locomotion/squat/torso into low-dim channels
  and end-effector targets. The un-smoothed 29-DoF pose-tracking reference is
  the hard mode; GR00T sidesteps the whole A2 class by commanding intents.
  (Aligns with the SONIC/GR00T-WBC note in memory as a future base-policy
  upgrade: intent-style command interface tolerates jitter far better.)
- **Even NVIDIA does no auto-reconnect**: order-critical startup, manual
  browser connect, no session recovery documented. Our resilience gaps are
  normal for this class of system — the fix is the adb/supervisor hardening
  above, not a magic upstream feature.
- **They validate by replaying recorded actions in sim** (replay_demos.py) and
  warn "jerky seed demonstrations lead to poor synthetic augmentations" —
  their answer to chop is operator practice + strong wireless, ours must be
  algorithmic (slew limit + interpolation) because we track raw pose.
- **Network guidance matches ours**: dedicated strong Wi-Fi (their CloudXR
  network setup guide = our "buy the dedicated router" runbook item; 5 GHz).
- Sim-first data collection with an IWER desktop emulator ≈ our
  `--fake-pico-stream` — worth keeping that path first-class for testing.
